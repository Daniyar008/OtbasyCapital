# Как приложение записывает данные в PostgreSQL

Это описание кода проекта, а не инструкция вручную добавлять операции через SQL.

## Регистрация

1. Кнопка «Тіркелу» вызывает `_register()` в `lib/features/auth/screens/auth_screens.dart`.
2. Экран вызывает `AppStore.register()` из `lib/app/app_store.dart`.
3. `SupabaseFinanceService.signUp()` в `lib/core/services/supabase_finance_service.dart`
   вызывает `client.auth.signUp(email: ..., password: ..., data: {'name': ...})`.
4. SDK отправляет HTTPS POST `/auth/v1/signup` в Supabase Auth.
5. Сервис Auth создаёт пользователя в `auth.users`. Пароль обрабатывает Auth;
   Flutter не сохраняет его в таблицах проекта и не пишет SQL INSERT в auth.users.
6. Если в Supabase включено подтверждение email, приложение показывает сообщение
   с просьбой подтвердить адрес. До подтверждения и входа данные аккаунта не открываются.
7. После получения сессии загружается персональный кэш или облачные записи.
   У нового аккаунта создаётся пустая семья и запись участника; примеры из урока не копируются.

Для DBeaver название пользователя находится в `auth.users.raw_user_meta_data ->> 'name'`.
Таблица `otbasy_members` - участники семейного бюджета, а не таблица паролей/авторизации.

## Вход

`_login()` → `AppStore.login()` → `SupabaseFinanceService.signIn()` →
`client.auth.signInWithPassword()` → POST `/auth/v1/token?grant_type=password`.
Сервер проверяет пароль и возвращает сессию. SDK сохраняет и обновляет её.
В таблицы через Data API отправляется JWT пользователя. RLS сверяет auth.uid() с user_id.
Открыть приложение с произвольным email без правильного пароля теперь нельзя.

## Добавление и изменение операции

`EntryFormScreen._save()` находится в `lib/features/transactions/screens/transaction_screens.dart`.
Он создаёт MoneyEntry с ID и передаёт его в `AppStore.saveEntry()`.

`saveEntry()` добавляет запись в список либо заменяет запись с тем же ID.
Затем `_changed()` передаёт состояние в `CloudStorageService.write()`.

В `lib/core/services/cloud_storage_service.dart` сначала сохраняются данные и очередь
изменений в отдельный Hive box `otbasy_cloud_<user UUID>`. Затем вызывается
`SupabaseFinanceService.upload()`. Если сеть недоступна, очередь остаётся в Hive.

В `lib/core/services/supabase_finance_service.dart` метод `_upsert()` содержит
реальную отправку данных:

```dart
await client.from(table).upsert(rows, onConflict: 'user_id,id');
```

Для операций `table` равен `otbasy_entries`. SDK отправляет POST на
`/rest/v1/otbasy_entries?on_conflict=user_id,id` с JSON телом и JWT пользователя.
Supabase Data API (PostgREST) переводит этот запрос в SQL для PostgreSQL.
По смыслу это `INSERT ... ON CONFLICT (user_id, id) DO UPDATE ...`.
Полного SQL текста с подставленными значениями в Flutter-файлах нет: его формирует сервер.

Перед операциями загружаются семья и участники, чтобы выполнялись внешние ключи.
Отправляются только изменённые операции/цели/напоминания, а не все старые строки.
Одинаковый ID означает UPDATE существующей записи; новый ID означает INSERT.

## Удаление, чтение, Favorites

- `AppStore.deleteEntry()` удаляет запись локально. Её ID попадает в очередь удалений.
  `upload()` выполняет `.delete().eq('user_id', userId).eq('family_id', 'family-main').inFilter('id', ids)`.
  Это HTTP DELETE и серверный SQL DELETE только для указанных записей владельца.
- `download()` использует `.select().eq('user_id', userId)` для чтения семьи и её данных.
  Это HTTP GET и SQL SELECT. Имя и сумма в интерфейсе берутся из загруженных строк.
- `toggleFavorite()` меняет поле favorite. Изменение сохраняется тем же upsert.

В DBeaver изменения видны после обновления таблицы или повторного SELECT.
Query Manager DBeaver не следует считать журналом всех запросов других приложений:
для показа данных используйте `supabase/inspect_app.sql`.

## Запуск и проверка на своём аккаунте

В `lib/main.dart` инициализируется Supabase, подключается CloudStorageService
и восстанавливается сессия. URL и publishable key проекта находятся в
`lib/core/config/supabase_config.dart`. Можно переопределить их через
`--dart-define=SUPABASE_URL=...` и `--dart-define=SUPABASE_PUBLISHABLE_KEY=...`.
Это публичные параметры клиента. Пароль PostgreSQL/service_role здесь не нужен.

Зарегистрируйте свой реальный email в приложении, подтвердите его при необходимости
и войдите. Добавьте операцию, затем измените её сумму. В DBeaver выполните
SELECT из `inspect_app.sql`: тот же ID должен получить новую сумму и updated_at.
Проверьте Favorites и удаление. Это проверка настоящего облака, которую нужно
провести со своей сессией; автоматические SDK-тесты используют HTTP-имитацию.

## Поведение без сети и ограничения

Для первого входа и регистрации нужен интернет. Ранее сохранённая сессия и
персональный кэш позволяют продолжить локальную работу, пока SDK сохраняет сессию.
После ошибки очередь повторяется при следующем сохранении, открытии аккаунта
или по кнопке «Қайта синхрондау» в профиле. Облачная ошибка отображается отдельно
от успешного локального сохранения. Само восстановление сети не запускает фоновый таймер.

Сначала отправляется очередь, затем загружаются облачные данные. Новые аккаунты
не видят кэш других пользователей. Неотправленная очередь сохраняется и после выхода.
После успешной отправки она очищается. Записи, отсутствующие в локальном списке,
не удаляются из облака без явного ID в очереди удаления.

Realtime, приглашения разных аккаунтов в общую семью и разрешение конфликтов
одновременного редактирования одной записи не реализованы. Для одного и того же ID
побеждает последняя успешная отправка. Серия запросов к пяти таблицам не является
одной транзакцией: при частичном сбое вся незавершённая очередь остаётся для повтора.
Текущий SELECT рассчитан на учебный объём данных в пределах лимита API Supabase.
Восстановление пароля пока оставлено в прежнем учебном режиме.

auth.users кестесінде құрылады. Операция сақталғанда алдымен Hive жаңарады,
